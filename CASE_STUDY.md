# Case Study: Building an AutoML Platform That Doesn't Lie About Its Numbers

## The starting point

The first version of this project's ML modeling stage worked the way a lot of portfolio "AutoML" demos work: a large language model was handed a description of the dataset and asked to *describe* what training results would plausibly look like. It produced a confident, well-formatted accuracy score. It was fiction. No model was ever fit; no metric was ever measured.

That's the problem this project is actually about. Not "add machine learning to an app" — that part is a solved problem in a few lines of `scikit-learn`. The interesting problem was: once an LLM is already wired into your product for the UX it's genuinely good at (chat, narration, plain-English summaries), how do you stop it from also becoming the thing that quietly fabricates the numbers your users make decisions on? That question shaped almost every technical decision below.

## What was technically hard

**Making metric fabrication structurally impossible, not just discouraged.** A system prompt that says "don't make up numbers" is not a guarantee — LLMs are extremely good at sounding confident regardless. The fix was to stop asking nicely: the Gemini response schemas for narration endpoints (`/api/eda`, model explanations, hypothesis interpretation) simply don't have a slot for a number. `responseSchema` defines `summary`, `dataQualityFlags[]`, `recommendedNextSteps[]` — string fields only. Every actual metric in the UI is injected from the real computation *after* the model responds, or read directly from the Python service's JSON. If Gemini wants to lie about a number, there's no field to put it in. When there's no API key at all, the app falls back to a template narrative assembled purely from the same real numbers, rather than hiding the feature or hanging.

**Explaining a model-selection decision instead of hiding it.** Training five candidate models (Logistic Regression, Random Forest, Gradient Boosting, XGBoost, an MLP) is the easy part. The harder requirement was that the "winner" be genuinely justified and visible: ranking is done by 5-fold cross-validation mean rather than a single noisy test-set score, ties within a 0.005 CV-mean band are broken by lower fold-to-fold variance, and the exact reason ("Logistic Regression selected for the highest 5-fold cross-validation mean accuracy (0.8708)...") is generated from the same sort key that produced the ranking and shown in the UI — not a separate, potentially-inconsistent LLM-written explanation. During one real training run on the sample churn dataset, Logistic Regression won the championship with a *lower* raw test-set score (50%) than Random Forest (66.7%) because its cross-validation mean was far more stable (87.1% ± 8.5% vs. 81.1% ± 4.5%) — exactly the scenario this ranking logic exists to catch, and exactly the kind of result an LLM asked to "just report the best accuracy" would get wrong.

**A real SHAP bug, not a hypothetical one.** Wiring up SHAP explainability for five different model types surfaced a genuine bug: computing SHAP values for the MLP classifier crashed with a numba `TypingError` deep inside SHAP's masking internals. The cause was calling the explainer against `.predict()`, which returns string class labels (`"Yes"`/`"No"`) — SHAP's JIT-compiled masking code can't write strings into the numeric array it allocates internally. The fix was routing classification explainers through `.predict_proba()` instead, which was confirmed with a standalone reproduction script before touching the real code path, not guessed at from a stack trace.

**Verifying the demo, not just the code.** Building the demo recording for this README surfaced two real, pre-existing bugs that unit tests hadn't caught because they only exist at the UI-integration level: the built-in sample datasets were too small (15 rows) to clear the ML service's own honest 20-row training minimum, silently breaking the "one-click AutoML" flow for every sample dataset out of the box; and the sequential "Next Stage" navigation button relied on `hasRunAudit`/`hasRunEda` flags that were declared in context but never actually set anywhere, so it could never advance past the Cleaning Studio stage. Neither was caught by reading the code — both surfaced by actually running the app end-to-end and watching it fail. Both are fixed now.

**Finding a fabrication the same audit was supposed to prevent.** A late pass specifically auditing "is anything narrated when it should be computed" turned up the most serious issue in the whole project: the Hypothesis Testing Lab's "Run This Test" button computed its p-value with `Math.random()`. It rendered a confident significance verdict on every click, for a test that never ran. The fix was a genuine one, not a copy edit — a new `/hypothesis-test` endpoint that picks a real test (Pearson correlation, Welch's t-test, one-way ANOVA, or a chi-squared test of independence) based on the actual dtypes of the two chosen columns and computes it with `scipy.stats`, plus real column-picker dropdowns for custom hypotheses to replace a `columnsInvolved: ['Auto-detected']` placeholder that was never actually detecting anything. It's a reminder that "audit the copy" and "audit the code" aren't the same task, and that this project's central claim only holds if it's re-verified, not assumed, every time a new corner of the app gets attention.

**Making the agent's own honesty enforceable, not just requested.** The agentic analysis mode (Gemini plans a diagnostic, the plan is executed as a real function call, the real result feeds the next turn) needed the same treatment as the narration endpoints: Gemini is constrained with `FunctionCallingConfigMode.ANY` against a fixed, whitelisted tool list, so it can't invent a fourth action, and every tool's only free-text field is `reasoning` — the before/after metric shown for each step always comes from the real ml-service response, never from what the model says happened. The one real nuance that couldn't be fully engineered away: a `retrain_with_transform` call on the *target* column produces a metric on a different numeric scale (R² of a log-transformed target isn't strictly comparable to R² of the raw target), so rather than silently treat that as an apples-to-apples improvement, the step response carries a `targetWasTransformed` flag the UI surfaces as an explicit caveat.

## What I'd change with more time

**Split the frontend bundle.** The production build currently ships one ~2.3 MB JS chunk — Vite's own build output flags this. Route-level code-splitting (the dashboard, reports, and ML modeling stages don't all need to be in the initial payload) would meaningfully improve first-load time.

**Finish the ESLint pass.** This codebase had no linter history before this round of work. Wiring one up cold surfaced ~190 findings (mostly unused imports and a few real `react-hooks` issues); it's intentionally running as an informational, non-blocking CI check rather than a merge gate until that backlog is worked down deliberately instead of auto-fixed in bulk.

**Get a stable hosted demo up.** The Docker Compose setup makes local evaluation a one-liner, but there's no substitute for a real, always-on URL for a recruiter to click without opening a terminal.
